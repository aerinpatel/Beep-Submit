# Engineering Notes & Bug Log

This document records issues, root causes, and fixes encountered during the build. Every entry follows the structure: **Symptom / What I tried / Root cause / Fix**.

---

### Issue 1: PowerShell Script Execution Policy Blocking `pnpm` and `npm`

- **Symptom**: Running `pnpm` or `npm` in PowerShell fails with:
  `File C:\Users\...\pnpm.ps1 cannot be loaded because running scripts is disabled on this system. (PSSecurityException / UnauthorizedAccess)`.
- **What I tried**: Attempted running `pnpm --version` directly in PowerShell.
- **Root cause**: Windows PowerShell default execution policy prohibits running un-signed `.ps1` wrapper scripts generated by npm/pnpm.
- **Fix**: In Windows PowerShell sessions, execute `pnpm.cmd` and `npm.cmd` (the batch file shims) or run via `cmd /c pnpm ...`. Configured all tooling, package scripts, and workflow instructions accordingly.

---

### Issue 2: pnpm v11 Ignored Build Scripts Security Blocker (`ERR_PNPM_IGNORED_BUILDS`)

- **Symptom**: `pnpm install` halted with:
  `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.18.20, esbuild@0.19.12, esbuild@0.28.2. Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.`
- **What I tried**: Attempted adding `pnpm.onlyBuiltDependencies` in `package.json`, which is deprecated/moved in pnpm v11.
- **Root cause**: pnpm v11+ introduces strict supply-chain security by default, isolating postinstall lifecycle scripts (like esbuild platform binary installation) until explicitly whitelisted.
- **Fix**: Executed `pnpm.cmd approve-builds --all` to authorize required native build binaries for `esbuild` and `tsx`.

### Issue 3: Inconsistent Public ATS Board Slugs & TLS Handshakes on Scraping Targets

- **Symptom**: Querying arbitrary brand names on Greenhouse (e.g., `razorpay`, `swiggy`) returned HTTP 404, while public Reddit JSON endpoints failed with TLS trust errors in the execution environment.
- **What I tried**: Probed 50+ prospective company slugs across Greenhouse, Lever, Ashby, and RSS/social sources.
- **Root cause**: Companies frequently use third-party aggregator wrappers or customized ATS subdomains. Additionally, scraping social sites like Reddit triggers aggressive datacenter blocking / SSL handshake failures.
- **Fix**: 
  1. Selected verified public ATS API endpoints with documented public job boards (Greenhouse boards API, Lever postings API, Ashby job board API, and open syndication).
  2. Isolated each source runner with `Promise.allSettled` so that an error or 404 in one company or source never terminates the pipeline.
  3. Identified 27 high-volume tech employers with active India offices and early-career listings (e.g. InMobi, Groww, Deliveroo, Rubrik, Datadog, Coinbase, GitLab, Okta, MongoDB, Databricks, Twilio, Samsara, Zscaler, PureStorage, Paytm), fetching **639+ real fresher postings**.

### Issue 4: Content Hash Divergence Due to Corporate Entity Suffixes

- **Symptom**: Jobs with identical titles and cities at the same company produced completely different SHA-256 `contentHash` values when one source reported the legal entity name (e.g. `CRED Inc.` or `InMobi Technologies Pvt Ltd`) while another used the brand name (`CRED`, `InMobi`).
- **What I tried**: Raw alphanumeric string stripping on company name prior to hashing.
- **Root cause**: Corporate legal suffixes (`Inc`, `LLC`, `Ltd`, `Corp`, `Technologies`, `Pvt Ltd`) vary across ATS job board integrations, causing false negative duplicate detection.
- **Fix**: Added a legal suffix normalization pass in `lib/normalizer.ts` (`normalizeCompany`) that removes common corporate designations (`inc`, `llc`, `ltd`, `pvt`, `technologies`, `solutions`, etc.) before computing the SHA-256 content hash, guaranteeing deterministic duplicate matching across sources.

### Issue 5: Windows Host Service Collision with Docker PostgreSQL Port 5432

- **Symptom**: Starting the Docker PostgreSQL container mapped to host port 5432 resulted in `password authentication failed for user "postgres"` when connecting from host scripts.
- **What I tried**: Attempted connecting to `localhost:5432` with standard container credentials (`postgres/postgres`).
- **Root cause**: A pre-existing Windows host service (`postgresql-x64-18`) was already running and intercepting requests routed to `127.0.0.1:5432`, blocking traffic from reaching the containerized database.
- **Fix**: Remapped the Docker container's external port in `docker-compose.yml` to `5436:5432` (`beep-db`), while keeping the internal container network address as `db:5432`. Updated `.env` and verified both host scripts and container environments operate against the containerized database.

### Issue 6: Content Hash Discrepancy Between Seed Script & Canonical Normalizer

- **Symptom**: During Chunk 4 deduplication testing, incoming exact duplicate jobs matched via `canonicalUrl` but failed exact match on `contentHash` against records created by the seed script.
- **What I tried**: Checked `contentHash` values in Postgres vs those produced by `normalizePost`.
- **Root cause**: `scripts/seed.ts` contained an ad-hoc local `hashContent` helper rather than importing the canonical `computeContentHash` from `lib/normalizer.ts`. When `lib/normalizer.ts` was enhanced in Chunk 3 to strip legal corporate suffixes and sanitize non-alphanumeric chars, the seed script's hashes became stale.
- **Fix**: Refactored `scripts/seed.ts` to import `computeContentHash` directly from `lib/normalizer.ts` and re-seeded the database, ensuring strict hash parity between the pipeline and seed records.

### Issue 7: LLM Response Markdown Wrapping in JSON Mode

- **Symptom**: When requesting structured JSON output from LLMs with `response_format: { type: "json_object" }`, certain models wrap the response in markdown code fences (`\`\`\`json ... \`\`\``), which causes standard `JSON.parse` to throw a `SyntaxError: Unexpected token '`'` error.
- **What I tried**: Relying solely on `response_format: { type: "json_object" }`.
- **Root cause**: Open-source models (including `gpt-oss-20b` and Llama variants) frequently prepend and append markdown code fences in their chat completions.
- **Fix**: Added a resilient sanitizer in `lib/tagger/index.ts` that strips leading and trailing markdown backticks (`\`\`\`json ... \`\`\``) prior to JSON parsing and Zod schema validation, with an automated 1-retry fallback.

### Issue 8: Node.js v22 Crypto Hashing Failure on JavaScript Date Objects in SQL Driver

- **Symptom**: Stage 5 (Postgres Upsert) failed with `FATAL PIPELINE FAILURE: The "string" argument must be of type string or an instance of Buffer or ArrayBuffer. Received an instance of Date`.
- **What I tried**: Passing native JavaScript `new Date()` instances directly into tagged template SQL expressions `${new Date()}`.
- **Root cause**: In Node.js v22, `postgres.js` hashes prepared query statement parameter values using `crypto.createHash().update(val)`. Passing non-string, non-buffer objects (such as `Date`) into `crypto.createHash().update()` triggers a strict TypeError in Node v22.
- **Fix**: Converted all timestamp values to ISO 8601 strings (`new Date().toISOString()`) before passing them to SQL expressions. PostgreSQL natively parses ISO timestamp strings into its internal `TIMESTAMP` representation, preventing any Node.js driver hashing exceptions.

### Issue 9: Pipeline Re-Run Deduplication Overwriting Primary Records (`is_duplicate_of = id`)

- **Symptom**: After running the daily ingestion pipeline a second time, active job count on the UI plummeted from 419 to 4. Over 400 primary jobs were marked as duplicates with `is_duplicate_of` pointing to their own UUIDs (`is_duplicate_of = id`).
- **What I tried**: Inspecting the `is_duplicate_of` values in PostgreSQL and comparing them against `id`.
- **Root cause**: In `lib/dedupe.ts` (Layer 2 DB exact match), incoming posts were queried against `posts` via `WHERE canonical_url = ... OR content_hash = ...` without excluding the post's own record (`NOT (source = post.source AND source_id = post.sourceId)`). On re-runs, the database lookup matched the post's own existing primary row, assigned `isDuplicateOf = existingRow.id`, and on upsert set `is_duplicate_of` to its own ID.
- **Fix**: 
  1. Updated `lib/dedupe.ts` Layer 2 and Layer 3 SQL queries to explicitly exclude the candidate's existing record (`AND NOT (source = post.source AND source_id = post.sourceId)`).
  2. Preserved previous duplicate status if a post was already legitimately linked to another root post.
  3. Added an explicit guard in `lib/pipeline.ts` preventing `is_duplicate_of` from ever being set equal to `id`.
  4. Executed `UPDATE posts SET is_duplicate_of = NULL WHERE is_duplicate_of = id;`, restoring all 419 primary active jobs.

### Issue 10: Groq Free Tier Tokens-Per-Minute (TPM) Rate Limit (HTTP 429) on Sequential Batches

- **Symptom**: When tagging 23 consecutive batches of 15 posts (~3,500 tokens per batch), batches after the 2nd one threw `HTTP 429: Rate limit reached for model openai/gpt-oss-20b: Limit 8000, Used 7992`.
- **What I tried**: Immediate 1-retry fallback without pacing.
- **Root cause**: Groq's on-demand free tier enforces a strict 8,000 tokens-per-minute limit for `openai/gpt-oss-20b`. Two consecutive batches exhaust the per-minute quota immediately.
- **Fix**: Relied on `contentHash` caching to retain tags across runs, and configured polite delays/backoff between LLM batch requests.

### Issue 11: Server Component Rendering Error with Unhandled ECONNREFUSED

- **Symptom**: Web UI failed to render with generic Next.js runtime error: `1 of 1 error Next.js (14.2.18) Unhandled Runtime Error: An error occurred in the Server Components render but no message was provided` at `app/page.tsx:155`.
- **What I tried**: Inspecting terminal logs for the running Next.js dev server.
- **Root cause**: The Docker PostgreSQL container (`beep-db`) was temporarily stopped or unreachable, causing raw database queries inside the Server Component to fail with `ECONNREFUSED` without a contextual user-facing error boundary.
- **Fix**: Wrapped database querying inside a structured `try / catch` error boundary, and added a retro diagnostic notice in `app/page.tsx` that alerts the developer to start the database container (`docker compose up -d db`) while preventing page crashes.

---

### Issue 12: Monolithic Page Component Coupling Data and Presentation

- **Symptom**: `app/page.tsx` expanded to over 600 lines containing raw SQL queries, UI templates, hero markup, badge formatters, and pagination controls in a single monolithic file.
- **What I tried**: Maintaining everything in one page component.
- **Root cause**: Monolithic component structures reduce code readability, make unit testing cumbersome, and create tight coupling between rendering and database logic.
- **Fix**: Modularized `app/page.tsx` into concise, reusable components (`Navbar`, `Hero`, `SearchFilters`, `JobCard`, `Pagination`, `Footer`) in `components/`, reducing `app/page.tsx` down to under 100 clean lines.

---

### Issue 13: Direct Raw SQL Queries in Server Component Migrated to Prisma ORM

- **Symptom**: Raw PostgreSQL string queries with tagged template literals were embedded directly in UI page components (`app/page.tsx`), creating potential maintenance hazards and tight coupling to specific SQL syntax.
- **What I tried**: Keeping raw SQL queries in `app/page.tsx`.
- **Root cause**: Lack of an ORM abstraction layer made typed data access, relation handling, and schema introspection difficult to manage in the web UI.
- **Fix**: 
  1. Configured Prisma ORM (`prisma/schema.prisma`) with models `Post`, `Run`, and `LlmUsage`, mapping snake_case PostgreSQL columns to idiomatic camelCase TypeScript properties.
  2. Created singleton Prisma client (`lib/db/prisma.ts`) preventing multiple client instances in Next.js development mode.
  3. Created dedicated Prisma data service (`lib/db/jobs.ts`) encapsulating `getJobs()`, using `prisma.post.count()` and `prisma.post.findMany()` for filtered listings and `prisma.$queryRaw` for PostgreSQL full-text `tsvector` ranking.
  4. Fully removed all raw SQL strings from `app/page.tsx`.
